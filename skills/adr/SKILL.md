# ADR 作成スキル

**決定済みの判断を、事後に、不変の履歴として記録する**。フォーマットは Michael Nygard 形式（Title / Status / Context / Decision / Consequences）に準拠。

ADR は設計メモではない。検討中の案・実装手順・TODO・現状の仕様説明を置く場所ではない。

## ADR にするかの判定

以下を**すべて**満たす時だけ書く。1つでも欠けたら ADR にしない。

- 判断が既に確定している（検討中・提案中は対象外。Status: Proposed も原則使わない）
- 覆すのにコストがかかる（容易に戻せる判断は記録に値しない）
- コードを読んでも「なぜそうしたか」が分からない（何をしたかはコードと git log が語る）
- 影響がモジュール横断、または長期に残る

ADR にしないもの → 置き場所:

- 実装計画・作業手順・TODO → issue / PR 本文
- 検討中の案の比較、設計ドラフト → issue / PR 本文（決まったら ADR に落とす）
- 現状の仕様・構成の説明 → README / docs（SPEC であって ADR ではない）
- 調査ログ、試行錯誤の記録 → 会話 or 作業メモ
- 自明な選択（言語標準の作法、バージョン上げ、命名）→ 記録不要

迷ったら書かない。ユーザーが `/adr` を明示的に呼んだ場合でも、上記に照らして ADR 向きでなければ、その旨と代替の置き場所を伝えてから判断を仰ぐ。

## 使い方
`/adr <判断の概要>`

例: `/adr Redisをキャッシュに採用する`

## 手順

1. 既存の ADR ディレクトリを確認し、次の連番を決定する
   - **`doc/adr/` と `docs/adr/` の両方を見る**。リポジトリが既に使っている方へ書く（勝手に片方へ寄せるとディレクトリが分裂する）
   - ファイル名: `NNN-<slug>.md`（例: `003-use-redis-for-cache.md`）
   - slug は英語のケバブケース、簡潔に
2. ユーザーの入力と現在のコードベースから Context を理解する
3. 以下のテンプレートで ADR を作成する

## テンプレート

```markdown
# ADR-NNN: <タイトル（日本語）>

## Status

Accepted (YYYY-MM-DD)

## Context

<なぜこの判断が必要になったのか。背景・課題・制約を記述>

## Decision

**<判断内容を1行で太字。過去形・確定形で書く（「〜する」であって「〜してはどうか」ではない）>**

<採用理由を箇条書きまたは段落で補足>

<検討したが採用しなかった案と、却下した理由。これが無い ADR は設計メモと区別がつかない>

## Consequences

<この判断による影響。良い点・注意点を分けて記述>
```

## ルール

- 本文は日本語で書く
- 日付は今日の日付を使う
- どちらのディレクトリも無ければ `docs/adr/` を作成する
- 1 ADR = 1 決定。複数の判断を1ファイルに詰めない（詰めた時点で設計メモ化する）
- **ADR は日付付きの不変な履歴**。後から現状説明を追記して育てない（「適用実績」のようなセクションを足すと SPEC 化して腐る）。決定が変わったら編集せず、新しい ADR を書いて旧を `Superseded by ADR-NNN` にする
- 作成後、ファイルパスと概要をユーザーに報告する
